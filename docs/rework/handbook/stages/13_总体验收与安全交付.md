# 阶段13 · 最终统一验收、版本归档和远端交付

## 唯一需求

在所有独立整改阶段后完成整体验收、追溯和安全交付。**不再开发新功能。**

## 验收门槛

1. 阶段00–12报告齐全，存在确切的 Git SHA、修改文件、真实运行日志与视觉证据。
2. 用户明确提出的6大问题分别有整改对照：线稿生长、中央进度条、模型观感、镜头摄影、双栏布局、内饰真实视角；再检查 UI 信息减法和反向滚动。
3. 任何需要高精原始模型的任务若缺少文件，需明确 `BLOCKED`，不能在最终报告中写“全部完成”。
4. `npm run build` / 项目已有测试命令能成功；桌面和移动端至少各有截图。真机/浏览器未测一律标 `UNVERIFIED`。
5. 重要安全性质：单 Canvas、资源单实例、镜头控制权互斥、旧版参赛文件可恢复、版权信息完整。
6. 新版三张展板、说明 PDF、交互图、演示视频都可打开且规格合规；所有示意图和截图真实可信。

## 完成步骤

1. 运行 `git status`、对比整改分支与 main 的 diff；检查是否误改了 `.gitignore`，是否把368MB原始 GLB 或参考录屏提交进公开仓库。
2. 实际跑构建及视觉 QA 脚本，整理最新结果；不能仅引用旧 `docs/reports/FINAL_QA.md`。
3. 保存最终演示视频：从开场空缓存启动到自由探索并反向退出，能一眼看到整改成果。
4. 将所有阶段报告汇总为 `docs/rework/FINAL_REVIEW.md`，写明每个整改点原问题、修改文件、证据路径、结论、剩余风险。
5. 生成面向用户的简明 `docs/rework/DELIVERY.md`：运行指令、远端分支、最新 commit、线上预览（若确实已部署）、展板/PDF/视频位置。
6. 逐阶段 Git 提交完毕后，`git fetch origin` 检查冲突；可安全推送独立整改分支到 `origin`，必要时创建 PR。不能覆盖或强推 main。
7. 仅在自动化和人工视觉审核通过、仓库权限允许且无分支保护障碍时才实施受控合并；否则保留 PR/分支待审，不要冒充已合并。
8. 最终一次性向用户报告：哪些完成、哪些被阻断、准确的文件位置和提交。禁止“已经完美复刻”“所有设备60fps”等无证据评价。

## 建议报告格式

```md
# S90视觉整改最终交付
- 原main HEAD：
- 当前整改分支与HEAD：
- 已实现：逐项对应用户6项反馈，链接截图/录屏
- 未完成/BLOCKED/UNVERIFIED：
- 编译与测试结果：命令 + 环境 + 摘要
- 三张参赛展板的文件与规格：
- PDF / 演示视频位置：
- 远端branch/PR地址（若真实存在）：
- 原版成果保护说明：
```

## 终止条件

只有真实达到验收门槛、且交付资料完整，才能结束为 `COMPLETED`。如果确有硬阻断，则结束为 `PARTIAL_WITH_BLOCKERS`，如实列明已完成的独立需求与未完成的必须项。此次请求为**一次启动，Agent内部自动推进**，不需要让用户依次发送13条“开始阶段”指令。
